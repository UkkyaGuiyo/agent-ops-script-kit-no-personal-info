# 初めて使う人へ：履歴掃除係は何をする？

## 一言で

**「受け皿の古い記録を調べ、あとで見直す候補を挙げる係」**。ファイルを削除したり、Git履歴を掃除する係ではない。

複数の拾い係から届いた通知や、その後の処理状態は第4号の共通受け皿に記録される。記録は溜まっていくので、終わったものを保存期限に応じて見直す必要がある。しかし、**まだ処理中の記録は絶対に候補にしてはいけない**。

## 具体例

保存期限が90日なら、90日前に最終的に`reported`へ進んだアイテムは**期限候補**に入る。89日23時間59分しか経っていなければ入らない。初めて受け取った日時から90日ではなく、**終端状態に到達した日時**から数える。`unprocessed`と`audited`は候補にしない。

リマインダー由来の記録なら、アイテム本体が期限候補になっても状態イベントを保持する必要がある。エラー行も現在は消さず、稼働履歴の保持期限が決まっていない場合は保留する。由来が分からない場合も、勝手に「安全」とは考えない。

## 「候補」と「削除していい」は違う

今の公開受け皿では、重複排除の記憶がイベント列から作られる。古い行を消すと、その記憶や状態の再構成が壊れる可能性がある。したがって、**この係の`candidate`は「日数の条件を満たす」という意味だけ**で、**`safe_to_delete_count`は常に0件**。どのイベントも実際に消さない。

内部版では、掃除の準備記録と完了記録、読み戻し検証などの仕組みがあると報告されている。しかし、それは今の公開実装にある機能ではない。内部版も実際の削除が運用で発生した証拠は未確認。

## AIが説明するときの最低条件（C-7）

1. 「ファイル」ではなく「第4号・共通受け皿の記録」を対象にする。
2. `reported`/`discarded`の期限を確認し、`unprocessed`/`audited`は絶対に候補にしない。
3. `candidate`は実削除でも削除許可でもない。`safe_to_delete_count=0`。
4. リマインダーの状態イベント、エラー行、seen（重複排除記憶）、prune_log（掃除自身の記録）は保護する。
5. 第4号公開v1に内部版`prepare/complete`とseen分離が無いため、安全な記録削除は実証できない。
6. 保留（exit2）と正本異常（exit1）を区別し、どちらも「対象なし」と説明しない。
7. 元の時刻・ID・行・ファイルは変更しない。90日は設定値、実行間隔・自動削除は存在しない。

**手動で期限候補を調べるだけ**。削除を判断する人間にも、根拠の無い安全宣言を渡さないこと。
