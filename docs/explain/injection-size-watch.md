# 投入量見張り係を初心者へ説明する

**何を見張る？** AIが毎回の会話に自動で持ち込む、記憶や手順書などのファイルの大きさ。たとえば1つの資料が60,000 Bを超えたら、増え過ぎていないか確認を促す。60,000 Bは変更できる例の値で、普遍的な上限ではない。

**なぜ測る？** 毎回読まれる資料が大きくなると、何度も長い情報を扱うことになる。ファイルのバイト数を追うと増減の傾向が分かる。ただしファイルサイズから会話の正確なトークン数・金額・時間の削減は計算できない。

**普段はどうする？** 対象別のB数と合計を測り、履歴を更新するだけ。超過しなければ静かに終了する。週次増加を比べられるのは、少なくとも7日前の測定記録がある時だけ。分からない時はUNKNOWN。

**超過したら？** 別の私的フォルダへ、元データのバックアップ、分類候補、削減候補、バイト数の比較、自己テストを書き出す。元のファイルを1バイトも書き換えない。JSONは余分な空白を詰められるが、一般の文章は意味を壊さない保証がないので原文のまま下書きにすることがある。削減0 Bでも失敗ではなく安全な結果。

**A〜Fは何？** この公開版で便宜上使う分類。Aは残す、BはJSONの見た目だけ整理、Cは圧縮を検討、Dは必要時に読む資料へ移す検討、Eは削除を検討、Fは人間などの意味判断が必要。**元の内部のA〜Fの意味を再現したものではない**。C/D/Eは本人の別途判断を要求する。

**自己テストで何が分かる？** バックアップが一致するか、JSONのデータが変わっていないか、書き出した下書きの実際のB数はいくつか、など。『人が必要とする要点を下書きだけから思い出せるか』までは機械で断言しないので、意味の判定欄はNOT_ASSESSABLE。

**何が危険？** 読めないファイルを0 Bとするのは危険。失敗したらエラーにし、全体の合計を出さない。バックアップや下書きには本物の記憶や手順の本文が残るので外へ公開しない。実行結果の公開もしない。

**誰が決める？** 調べる対象と上限、意味を変えて良いか、最終的に何を削るかは人間。見張り係はあくまで**測る係**。下書きは作るが、元のファイルへの適用はこのツールの役割ではない。
