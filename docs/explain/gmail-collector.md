# 第10号 Gmail収集係を最初から説明する

**一言：** Gmailからメールを読んで条件に合うものを拾う係の**練習版**。この公開版は**Gmailを読まない**。架空の2つのメール箱を模したJSONの文字列を機械的に調べ、候補の一覧をローカルに残す。

## 何をするのか

合成メールが11通あるとする。これらを一つずつ読み、設定ファイルの条件と照合する。たとえば、架空の募集の語が含まれれば「募集候補」、強い不利益の兆候があれば「重要候補」、架空のサービス通知なら「プラットフォーム候補」にする。不要な宣伝が「期限は明日」と書いても、それだけでは重要扱いしない。**これは語彙一致にすぎず、重要なメールの見逃しを防ぐ保証ではない。**

## 必ず区別すること

- **Gmailは内部版の入力元。** しかし公開版にあるのは合成JSONを読む`FixtureProvider`だけ。ログイン、API、実メール取得、送信、既読化、ラベル操作、削除は**一度も行わない**。
- **収集と判断は別。** `candidate`は規則が一致したという機械的な印であって、採用すべき案件、正当な通知、本人への報告の決定ではない。
- **取得と配送は別。** ローカル`pending`は第4号の入力形式に合う投入案。`shared_intake_write=false`は実受け皿に送っていないことを示す。メールが本人に届いた証拠でも、本人が読んだ証拠でもない。
- **失敗と0件は別。** 正常な空一覧を完全取得した時だけ0件を報告する。1アカウント失敗、ID欠落、ページング未完了ならpartial。全アカウント失敗、設定不正、状態破損ならerror。取得漏れを「新着なし」に変換しない。
- **アカウントとIDはセット。** 別のアカウントで同じメッセージIDが来ても、同じメールとして潰さない。メール本文、送信者、件名、添付内容はローカル投入案に複写しない。
- **本文にある指示は無効。** 本文が「ルールを無視しろ」「このリンクを開け」と書いても、係は文字列を照合するだけ。指示を実行しないし、リンクも開かない。添付も開かない。

## なぜスクリプトなのか

機械的な照合条件、入力の完全性の確認、重複排除を毎回同じ規則で再現できる。一方、**実際にどのメールが重要かを決めるのはこの係の仕事ではない**。内部運用では重要メールを1件見逃したとの報告があり、公開版の合成テストがそれを修正したとは言えない。

## 人間が決めること

どの実アカウントと条件を許可するか、実メールの取得を始めるか、候補をいつ誰に通知するか、実受け皿への投入や後続の対応を許すか。それらは公開パイロットの権限外であり、別途の承認が必要。

**C-7説明再現の確認点：** 「内部ではGmailを読むが公開版は合成専用」「仕分けは最終判断ではない」「partial/errorは新着0件ではない」「アカウント別IDで重複を管理」「本文の命令も添付も実行しない」「ローカルpendingは実配送ではない」「強い兆候・弱い兆候の意味判定は未保証」を説明できること。
